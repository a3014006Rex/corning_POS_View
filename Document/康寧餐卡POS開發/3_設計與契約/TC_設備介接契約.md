# TC 設備介接契約草案

版本 v1.0。BF-Mini 與 DM-760 的確切原廠、韌體及封包尚未確認。本檔定義要取得的證據及新平台內部契約，不虛構原廠欄位或控制命令。

## 1. 每型設備須補齊的規格

| 類別 | 必要資料 | 完成證據 |
|---|---|---|
| 識別 | 原廠、完整型號、韌體、控制器與讀卡頭關係 | 照片/型號記錄與原廠文件版本 |
| 傳輸 | TCP Client/Server、Port、RS232、USB、SDK；可同時連線數 | 隔離設備連線與擷取記錄 |
| 會話 | 初始化、認證、查詢、心跳、時間同步與停止方式 | 命令與回應逐項對照，不使用正式金鑰進文件 |
| Frame | 長度、起訖、編碼、檢查碼、未知類型與錯誤碼 | 每型至少有正常、半包、黏包、壞包測試樣本 |
| 卡號 | 原始 bytes、進位、順序、是否截碼、是否應用卡號 | 測試卡人工值、設備原文與解析值對照 |
| 時間 | 設備日期、精度、時區、校時與重啟後狀態 | 跨午夜、偏差與補傳樣本 |
| 事件 | 設備 ID、序號範圍、重啟/回繞識別、重傳條件 | 可辨識同事件重送與第二次合法刷卡 |
| 保存 | 容量、游標、ACK、刪除與覆寫、下載是否清除 | 停止/中斷/恢復實驗；保留資料損失限制 |
| 卡名單 | 新增、銷碼、有效期、黑名單、全量重設與回應 | 下發與實際設備驗證，列維護時段限制 |
| 提示 | 蜂鳴、顯示、准用拒絕回傳與 POS 責任 | 卡機讀到卡與計費成功提示分開驗證 |


## 2. C# 原型可參考與需新增

- 已有：TCP 連線、建立連線逾時、重連、raw HEX/ASCII 顯示與文字日誌。
- 未有：各型 frame 分框、卡號與時間解析、協定 ACK/查詢/心跳、資料持久工作狀態、正式交易寫入、RS232。
- EnableDatabaseWrites 目前只顯示設定，不能作為已能寫正式 DB 的證據。
- 每次 ReadAsync 是接收片段，不保證等於一筆完整刷卡紀錄。文字 raw log 可診斷，但不能代替可恢復的確認點。
- overtime 文件與程式的秒/毫秒語意不一致，T02 以原廠規格及現場值核對，不直接修改正式設備。

## 3. Gateway 內部事件契約

| 欄位 | 規則 |
|---|---|
| GatewayId / DeviceId / ReaderId | 來自經授權與版本化設備設定，包含實際事件來源 |
| SourceEventKey | 來源系統＋設備穩定序號，含必要 boot/epoch；重送保持相同 |
| RawDataRef / RawHash | 受限存取的原始 frame／持久檔位置與完整性資訊 |
| RawCardCode / CardCode / EncodingVersion | 原值與正規值分開，卡碼保留前導零 |
| DeviceTime / ReceivedAt | 設備時間與接收時間，包含來源時區及可疑偏差 |
| ParserName / ParserVersion / FrameType | 指明實際解析器與類型，未知類型列異常 |
| Cursor / AckState / AttemptCount | 協定確認點與上送狀態，不能只靠本機目前時間去重 |
| ValidationResult | 完整、壞包、未知、缺時間或無法識別等原因，不帶猜測的員工 ID |


若設備沒有穩定序號，需在 T02/T16 定義持久接收位置與協定去重方案。單純 RawHash＋卡號＋秒數可能把合法再次刷卡誤判，不能無條件宣告一次作用；無法辨識的限制要列入驗收與人工處理。

## 4. 保存與確認順序

接收 bytes → 累積分框 → 驗證 → 持久保存 → 依協定 ACK/推進游標 → 上送 E11 → 保存中央接收結果 → 重試未確認事件。若原廠要求不同時序，需提供可證明不漏單的調整設計。

ACK 可能只是設備傳輸確認，不代表 POS 或金額已成功。中央回報同一事件已存在仍應回穩定結果，Gateway 不因重試重建 SourceEventKey。

## 5. 現場驗證控制

T02 先用隔離設備與測試卡。確認是否獨占連線、下載後是否清除紀錄、銷碼與設碼影響，再決定觀測方式。未確認前不在正式餐期雙開接收器、不送清空名單、不修改韌體或設備金鑰。

取樣紀錄至少包含設備/韌體、規格版號、合成卡別、人工刷卡時間、原始 frame、解析欄位、序號、命令/回應、重試與結果。實際卡號如不得避免，限制存取並在對外文件遮罩。
