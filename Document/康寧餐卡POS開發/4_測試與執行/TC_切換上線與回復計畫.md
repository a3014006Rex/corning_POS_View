# TC 切換上線與回復計畫

版本 v1.0｜T32 執行前由客戶 IT、餐務、財務、DBA 與維運共同定案。本版沒有進行部署、設備改寫或資料移轉。

## 1. 上線前置條件

- Q01–Q12 影響上線的決策已確認；設備接口、授權、身分源、收款邊界與離線策略完整。
- T31 的適用一期案例完成，實體設備、多餐道、補傳、交易查單與補助併發通過；未解釋帳差為零。
- 財務核准費用映射及報表/結算口徑；卡片撤銷同步與歷史歸屬通過。
- 備份及回復已在隔離環境演練，有舊新版本、設定、來源游標、差額核對與維運窗口。
- 單一計費權威、設備接收者、切換時間、核准人與回復觸發指標已記錄。

## 2. 觀測與切換步驟

| 序 | 動作 | 證據與責任 |
|---|---|---|
| 1 | 確認舊系統是目前唯一計費來源，新平台僅觀測比對 | PM/財務核對寫入與下游請款來源；設備不允許雙接收則用核准鏡像或隔離測試 |
| 2 | 選餐期間隔或核准停機窗口，公告作業方式 | 客戶餐務/IT 確認窗口與人工備援 |
| 3 | 停止新交易受理，排空或標記正在處理的請求 | 保存 ClientTransactionId、設備序號/游標、待確認、補傳及同步工作 |
| 4 | 完成來源快照、最後增量與截止點對帳 | DBA/財務保存筆數、金額、卡片生效與差額明細 |
| 5 | 關閉舊計費或下游出帳，切換設備接收與新平台授權 | 維運驗證只有一個正式寫入者與結算來源 |
| 6 | 小範圍核准試交易，查單及沖正並核對 | POS/財務確認事件、身分、金額、分攤與外部作用（若有） |
| 7 | 依餐道擴充，完整餐期觀察 | 收集故障、未知結果、解析失敗、同步積壓與帳差 |
| 8 | 確認第一個完整對帳與交接 | 客戶簽認，保留版本、窗口、操作手冊與告警 |


## 3. 回復觸發

帳差、錯人錯餐道、無法查明的交易結果、設備不穩、補助競爭錯誤或效能不符等，均應有 Q12 核准的門檻及判斷人。嚴重錯誤先停止新授權並保留證據，不直接清 DB 或重建交易。

## 4. 回復程序

1. 停止新平台新交易；保存全部成功、待確認、沖正、Outbox、卡片撤銷與補傳。
2. 以穩定交易 ID 查清已提交與外部作用，避免在舊系統重送同筆費用。無法查清者列人工處理，不能按失敗重扣。
3. 建立新平台運行區間的交易與卡片異動清單，決定如何供舊平台及財務接續。
4. 先驗證舊平台資料與卡片名單能銜接最新撤銷及結算；不具銜接能力時維持人工備援，不強行開舊平台授權。
5. 經客戶核准後恢復舊平台單一計費與設備接收；隔離新平台的寫入與下游結算。
6. 新平台資料保持可查與可對帳；修復後以新切換計畫再試營運，不覆寫原成功紀錄。

只回復舊 DB 快照會遺失切換後交易與掛失異動，不能單獨當成回復方案。部署回退與帳務資料回復是兩件事。

## 5. 演練與交接紀錄

記錄時間/時區、核准者、舊新版本、唯一計費來源、來源游標、各狀態筆數與金額、卡片撤銷差額、告警、外部查單結果、回復耗時與未完成項。對應 A36；交接後由誰每日看積壓與對帳、誰接設備/卡務/財務問題，應列姓名與代理人，由客戶提供，不預填。
